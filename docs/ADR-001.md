# ADR-001 — Feature-oriented modules and handlers for CELD

- **Group:** 4
- **Profile:** D (feature modules, feature handlers, feature/integration emphasis)
- **Status:** Accepted **initial architectural decision** in the conversation; this written revision documents implementation choices.
- **SRS:** Approved CELD SRS v1.1.1 (`docs/SRS-v1.1.1.md`)
- **Important provenance:** A separately uploaded **revised ADR** was not available among the provided files. This document implements the Group 4/Profile D decision already discussed, with explicit SQLite-specific choices that require verification against the instructor environment sheet. It is not evidence of instructor approval for those choices.

## Context

CELD is a complete browser-based lending desk. The mandatory design challenges are server-side role/ownership authorization (BR-AUT-001–003), a database-enforced maximum of one active reservation per item (BR-RES-002), exactly three valid transitions (BR-RES-003), and successful creation/transition together with a History Event (BR-RES-004). Release acceptance includes real-relational tests for concurrent reservations and forced persistence failure.

## Decision

Organize the ASP.NET API under **Authentication, Catalog, Reservations, and Lending feature modules**. Mutation handlers are intention-revealing: `CreateReservation`, `CancelReservation` via `ReservationTransitions`, `RecordPickup`, and `RecordReturn`. Queries return explicit DTOs, never EF entities or password hashes. Cross-cutting components are limited to database configuration, authorization/session validation, CSRF middleware, uniform errors, and shared transition policy.

### Rule enforcement ownership

| Rule | Concrete enforcement |
|---|---|
| BR-AUT-001 | `Security/SessionValidator.cs` revalidates server-side session; `CurrentActor.cs` derives ID/role from signed cookie; `Features/Authentication/AuthEndpoints.cs` signs claims from provisioned account only |
| BR-AUT-002 | `Features/Reservations/ReservationEndpoints.cs` scopes `/mine`; `ReservationTransitions.cs` verifies ownership before cancellation; detail queries return 404 for other students |
| BR-AUT-003 | `/api/staff/reservations` route group requires Staff policy; Student cannot call pickup/return |
| BR-RES-002 | `Data/CeldDbContext.cs` creates **filtered UNIQUE SQLite index** on `EquipmentItemId` when status is `Reserved` or `CheckedOut`; `CreateReservation.cs` checks availability and translates expected unique/busy failures into 409 |
| BR-RES-003 | `Domain/ReservationLifecycle.cs` has the exhaustive three-transition policy; `ReservationTransitions.cs` uses it and compare-and-swap update by current status + version |
| BR-RES-004 | `CreateReservation.cs` inserts reservation and creation History in **one SaveChanges transaction**; `ReservationTransitions.cs` places conditional update + History insert in **one explicit EF transaction**; failure rolls back |

**Availability** is derived from persisted active reservations, never a separate client-authoritative or denormalized mutable flag.

## Consequences

Positive: feature-to-use-case alignment, focused integration tests and ownership checks, clearer traceability, local scope for future business changes. Negative: small repeated guard code, more files than a central service, need to coordinate shared policies, and provider-specific SQLite filtered index. EF `EnsureCreated` is suitable only for initial schema provisioning; production schema upgrades need a reviewed migration strategy before a database provider/version change.

## Alternative

A central `ReservationService` (Profile B) can reduce file count and group business operations together. It may be preferable for very small systems or where extensive shared policy coordination outweighs feature isolation. It risks growing into a high-coupling service. The Profile D design is the preferred initial hypothesis; acceptance depends on requirements and observed evidence, **not on architecture label**.

## Security assumptions and rejected shortcuts

- Never trust `userId`, `studentId`, or `role` from a request as an authorization credential.
- No public account registration or role-editing endpoints.
- Cookie sessions are **server-revocable** through `LoginSession`, and state-changing APIs require anti-CSRF tokens, including login and logout.
- No unprotected `PATCH status`, delete-history endpoint, plain-password storage, or JWT auth.
- Deployment must use trusted HTTPS and secret configuration; the SQLite demonstration provider must be approved or substituted per course sheet.

## Verification decision

`tests/Celd.Api.Tests/LifecycleUnitTests.cs` exercises the legal-transition policy; `FeatureIntegrationTests.cs` exercises normal and negative routes, staff/ownership authorization, persisted statuses, real SQLite double-booking race (AC-04), stale-action races, and SQLite trigger-induced History failure and rollback (AC-10). `PerformanceTest.cs` describes the 50/100 benchmark. Tests remain **NOT RUN** in this deliverable because .NET and npm dependencies are unavailable in the generation environment; use CI / local commands and record observed outputs and exact commit SHA.
